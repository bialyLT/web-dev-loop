## Cómo trabajamos (el loop)

```
dev (escribe)  →  tester (ataca, arregla, verifica)  →  gate del orquestador  →  cierre
```

- **Un solo escritor a la vez.** Mientras un agente escribe, los demás no tocan el árbol.
- **El orquestador es el único que commitea.** Los testers y el dev dejan el trabajo listo
  en el árbol y lo reportan; el commit lo hace el orquestador.
- **El tester es independiente y adversarial.** No confía en el informe del dev: lo
  reproduce con sus propios ojos. Cada bug lleva un **repro que falla primero**.
- **Los gates se reportan con números reales**, ejecutados. Un gate sin número no es un gate.
- **El cierre de cada ronda** deja: números por gate, informe escrito, memoria actualizada,
  commit convencional y push verificado.

## Reglas de repositorio y de commits

- Commits convencionales: `feat(scope): ...`, `fix(scope): ...`, `docs(scope): ...`.
- **ASCII simple en el mensaje** (PowerShell interpreta `$`, backticks y comillas dobles).
- **Sin atribución de IA**: nada de `Co-Authored-By`, nada de "generated by".
- Un commit por tarea. Los commits los hace el orquestador, nunca los agentes.
- `ROADMAP.md`, los informes y los logs de corrida son **locales** (`.gitignore`), si tu
  proyecto los tiene. El repo lleva código, tests y documentación de uso.
- Nunca se commitean carpetas de trabajo del harness (`{{SCRATCH_DIR}}/`) ni secretos
  (`.env`, `*.pem`, `*.key`).

## Entorno

- Base de datos local (si el proyecto la usa): `{{PG_DIR}}`, puerto `{{DB_PORT}}`
  (`{{DB_START_CMD}}`).
- El servidor se sirve compilado en `{{APP_PORT}}` para los tests end-to-end.
  **Parar el servidor antes de buildear** si el build toca binarios nativos (p. ej.
  `prisma generate` falla con EPERM si la DLL está cargada).
- **Un solo runner de UI a la vez** (Maestro / navegador / suite): comparten sesión y
  memoria; en paralelo dan `DevToolsActivePort file doesn't exist` o flows que tardan el
  doble.
- Para la suite de UI: `{{FLOWS_CMD}}` siembra la base y corre los flows en orden.
  Los flows **verifican**, no construyen: el escenario lo arma el smoke.

## Checklist de pre-vuelo del dev

Antes de escribir una línea, leé `docs/lessons.md` (o la sección equivalente en
`agents/dev.md`): son **clases de fallo**, pensadas para reconocer y resolver problemas
*similares*, no sólo la repetición exacta. Un test que tapa una lección no la poda.
